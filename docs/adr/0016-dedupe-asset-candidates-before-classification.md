# Asset candidates are deterministically de-duplicated before classification

The crawler captures `img.currentSrc` — one URL per `<img>` per page — so the
same original image served at different registered sizes or theme crops
across different page types becomes many distinct downloaded Asset
candidates. A real production Client (a 25-page WordPress plumbing site)
produced 117 image candidates that were mostly WordPress derivatives
(`-150x150`/`-768x512` core resize suffixes; `-scaled`/`-rotated`/
`-e{timestamp}` variants; TheGem theme crops like
`-thegem-gallery-fullwidth`/`-thegem-post-thumb-small`; cache-bust hash
suffixes) of a few dozen true originals. Handing all 117 to the classification
engine call inflated its cost and made it burn through its budget/turns
unreliably.

The only existing dedup is exact-URL: `ingest.ts`'s `seenAssetUrls` collapses
repeat `<img>` references to the identical URL, at crawl time. Nothing
collapsed *different* URLs that serve the same original image — that
judgment didn't exist anywhere in the pipeline before this change.

## Decision

A deterministic, dependency-free `dedupeCandidates` pass (`src/synthesize/assets.ts`)
runs over the candidate list in `runSynthesize` (`src/synthesize/synthesize.ts`),
right before the classification engine call. Three layers, in order:

1. **Exact byte-hash dedup.** A sha1 over each file's bytes collapses
   byte-identical candidates regardless of filename.
2. **WordPress derivative grouping.** `canonicalStem` strips the documented WP
   suffix conventions — `-WxH`, `-scaled`, `-rotated`, `-e{13-digit timestamp}`,
   retina `@2x`/`-2x` — to recover the original stem. A conservative
   bare-original prefix rule then folds `{stem}-{suffix}` into a captured bare
   `{stem}` candidate *only* when the suffix reads as a size/crop/derivative
   token (`looksLikeDerivativeSuffix` — a `-WxH` dimension, an opaque cache-bust
   hash, or a word from the size/crop vocab), keeping the largest-byte
   representative per original.
3. **Size floor.** Drops tracking pixels/spacers — raster candidates under
   ~1.5KB, or a `parseSizeSuffix`-parsed `-WxH` suffix under 32px — with
   SVG/ICO exempt.

## Why filename-based, and why conservative

WordPress derivative names are a stable, documented convention (WP core
itself uses the `-WxH` regex to detect autogenerated set members), so
filename grouping is cheap, deterministic, and reliable on the common case
without decoding a single image.

It is deliberately conservative to avoid false merges. It does **not** strip
the `-N` upload counter: in WordPress that suffix marks a genuinely distinct
upload whose name collided, and our own downloader's `uniqueName`
(`src/util/names.ts`) appends the same `-N` for the same reason — collapsing
it would merge unrelated uploads. The bare-original fold requires *both* that
the bare original was actually captured *and* that the differing suffix reads
as a derivative token, so `hero-left.jpg` never merges into `hero.jpg` just
because it shares a prefix.

Residual near-duplicates — e.g. a size-variant pair with no captured bare
original to fold into — are left as-is; the downstream singleton-role cap in
`reconcileAssets` already tolerates a small excess of same-role candidates.

This continues the ADR-0011/ADR-0014 through-line: deterministic code owns
the mechanical, decidable parts of Asset handling so the Engine only spends
judgment on what genuinely needs it. ADR-0011 moved *staging* out of the
Engine's task list because the keep/discard decision was already made
elsewhere; ADR-0014 stopped a flaky exit code from discarding a decision the
Engine had already made correctly. This ADR keeps an easy, decidable-by-code
judgment — "these are the same original" — from ever reaching the Engine's
classification call in the first place, rather than paying vision-model cost
and turns to have it notice the redundancy itself.

## Consequences

- The classification call sees fewer, more distinct candidates per Client,
  cutting its cost and turn count on asset-heavy sites without changing what
  it decides for any of them.
- `reconcileAssets`, `renderAssetsSection`, and everything downstream are
  unaffected — they still operate on whatever candidates classification saw
  and kept.
- Non-WordPress sites without these naming conventions pass through
  `dedupeCandidates` with only the byte-hash and size-floor layers doing
  useful work; the WP-specific layer is a no-op, not a liability, for them.

## Considered and rejected

- **Perceptual hashing (dHash/pHash).** The genuinely name-agnostic solution
  — it would catch same-image variants no filename rule can reach — but it
  needs image decoding, and no such dependency is present (Bun has no
  built-in decoder). Deferred; recorded in `NOTES.md` as a lever to pull only
  if this filename-based dedup proves insufficient on real non-WordPress
  sites.
- **Stripping the `-N` upload counter globally.** Rejected: in WordPress it
  marks a genuinely distinct upload whose name collided, and our own
  `uniqueName` overloads the same suffix for the same reason. Stripping it
  would risk merging unrelated Assets.
- **A curated per-theme slug denylist** (e.g. hardcoding TheGem's crop names).
  Rejected as fragile and per-theme; the bare-original + derivative-token rule
  generalizes the same intent without naming any one theme.
- **Dedup at download/ingest time.** Rejected: "keep largest" and the
  bare-original signal both need the full candidate set's byte sizes on disk,
  which don't all exist until ingest is done downloading everything. Ingest
  should also stay a faithful record of what the site actually served, not a
  stage that already makes judgment calls about which served copies matter.
