# Removal is the inverse of create: external teardown first, then gapless compaction

Every Client and Site Version accumulates state in three places that a create-path stage put there: the local folder under the Root (`generate`/`ingest`, ADR-0003), a hosted Cloudflare Pages deployment (`deploy`, ADR-0004), and — opt-in — one GitHub repo per Site Version (`push`, ADR-0004). Nothing in the tool removed any of it: a Client abandoned after outreach left a live `*.pages.dev` link and one or more private repos up indefinitely, plus their folder on disk. `sb remove` is the deliberate inverse of the create path, scoped either to a whole Client (`sb remove <client>`) or a single Site Version (`sb remove <client> --version n`).

## Decision

**Order is fixed: read pointers → tear down external → delete local → drop the CRM pointer → compact.** The Site Version pointers in `client.json` (deploy URL, GitHub remote) are the only record of what external resources exist; deleting the local folder first would strand a live site and repos with no way to find them again. So removal reads every pointer up front, tears down external resources, and only then touches local state.

**The two resource kinds are asymmetric, mirroring how they were created (ADR-0004).**

- *Cloudflare Pages is one project per Client* (`pagesProjectName(slug)`), and each `deploy` is a deployment inside it. Per-Version teardown therefore deletes a single *deployment*, found by listing the project's deployments and matching the one whose URL is the Version's recorded `deployUrl`. Whole-Client teardown — and removing the Client's last remaining Version — deletes the whole project instead.
- *GitHub is one repo per Site Version* (`<slug>-vN`), so teardown deletes exactly that repo.

**Both wrangler calls this deployment-level path depends on were wrong on first ship, in ways that silently no-op rather than error.** A real `sb remove --version n` run reported the deployment "not matched, skipping" for a URL that was demonstrably still live. Reading wrangler's actual handler (`src/pages/deployments.ts`, no `--json` schema is documented for this subcommand) found two bugs: (1) `wrangler pages deployment list --json` doesn't print the raw API deployment object — the handler maps each one to a *display* row with renamed, capitalized keys (`Id`, `Deployment` for the URL) before printing it, the same object it would otherwise hand to `logger.table()`; matching on lowercase `id`/`url` therefore matched nothing, every single time. (2) `wrangler pages deployment delete <id>` prompts for confirmation unless `-f`/`--force` is passed — and on a stdin-less, non-TTY spawn (exactly what `runCommand` gives it), wrangler's confirm helper resolves to `fallbackValue: false` and the handler returns *without deleting*, exiting 0. Even with bug (1) fixed, an unmatched deployment would have "deleted" successfully while staying live. Both are fixed: `parseDeploymentList` reads `Id`/`Deployment`, and the delete call always passes `--force`. `pages project delete` was double-checked against the same source and was already correct — it honors `--yes` as its own gate on the same confirm call, no separate trap.

**One Cloudflare restriction has no CLI-level workaround at all.** `wrangler pages deployment delete` (and the REST API underneath it) refuses to delete a project's *active production* deployment — the most recent deploy to `main` — with API error 8000034. This isn't one of the two bugs above; it's a real, permanent Cloudflare restriction, and it bites exactly the deployment for the highest-numbered surviving Version, since that's normally the one most recently deployed. Reading wrangler's own `pages deployment` subcommands (`list`/`delete`/`tail`, no more) confirms there's no flag or command to promote a different deployment to production first — that only exists as the dashboard's "Rollback" button, backed by a REST endpoint wrangler doesn't wrap, which would mean adding this codebase's only raw-API/token call outside the wrangler-CLI seam (ADR-0004) for one edge case. Instead, `deletePagesDeployment` detects this exact error (`isActiveProductionDeploymentError`, matched on the error text/code) and reports it as a **loud, non-fatal skip** rather than a failure: it's logged with the still-live URL, recorded in the outcome list, and local removal + Compaction proceed anyway. The deployment disappears for free the next time this Client's whole Cloudflare Pages project is deleted — `wrangler pages project delete` has no such restriction, and is already the path whole-Client teardown and "last remaining Version" teardown use.

**Teardown is best-effort and never silently orphans.** The active-production skip above is the one deliberate exception, and it's loud, not silent: the operator is told exactly which URL is still live and why, unlike a lost pointer. Each external delete is reported per resource. A Site Version with no recorded `deployUrl`/`remote` skips that step **with a warning**, so the operator knows a resource may still exist that the tool can no longer see. If any external delete *fails* (network, a missing `delete_repo` gh scope, an already-gone resource that errors), removal aborts before deleting local state — the pointer is the operator's only handle on the orphan — unless `--force` is passed to proceed anyway.

**Per-Version removal compacts the surviving Versions so the `vN` sequence is always gapless.** Removing v3 of v2–v5 shifts v4→v3 and v5→v4. The Version number lives in exactly three on-disk places, so a shift rewrites all three: the `sites/vN` directory name, the `version` field in that Version's generation `state.json`, and its `SiteVersionRef.version` in `client.json`. Its GitHub repo is also renamed (`<slug>-vN`) and the new remote read back and re-recorded; the Cloudflare deployment URL is immutable and not derived from the number, so it is left untouched. Shifts run in ascending order so each target slot is already vacated (no collisions). A dangling `targetVersion` on the context `state.json` that points at or above a removed Version is cleared.

**Safety is loud by default.** Removal confirms interactively (retype the slug) unless `--yes`; `--dry-run` prints the exact kill-list (folder, deployment/project, repo names) and exits without touching anything; `--local-only` removes local files and the CRM pointer while leaving external resources up.

**External calls sit behind injectable seams, like the create path.** A `CloudflareRemover` (mirroring `DeployRunner`) and a `GitHubRemover` (mirroring `GitHubPublisher`) default to the real `wrangler`/`gh` subprocesses and are faked in tests, so removal — the most destructive command — is exercised offline without ever shelling out or hitting the network (testing posture, ADR-0004).

## Consequences

- `config doctor` should note that repo deletion needs the `delete_repo` gh scope (non-gating, like the existing `gh` check).
- Compaction re-mints Version numbers, so `v3` after a removal is not the same generation as `v3` before it. A number identifies a slot in the current sequence, not an immutable generation id; the git history inside each `sites/vN` is the durable record.
- Renaming a GitHub repo changes its remote URL, so an old clone URL for a shifted Version stops resolving. Acceptable: these are private outreach repos, and gaplessness is the point.
- `setSiteVersions` is added to `storage/client.ts`, replacing the whole `sites` array in one write — dropping the removed ref and shifting several others (including a patched-in renamed remote) is one atomic change, not a sequence of per-ref merges like `recordSiteVersion`. Both keep `sites` sorted by version so `list`/`show` and compaction stay consistent (ADR-0003).
- Removing the Version whose deployment is Cloudflare's active production (typically the highest-numbered survivor) leaves that one deployment live on Cloudflare, under its old immutable URL, until the whole Client's Cloudflare Pages project is eventually deleted. A known, reported gap, not a bug — `sb remove --dry-run` flags it ahead of time via `mayBeActiveProduction`, and the run itself logs the exact URL left behind.

## Considered and rejected

- **Leave holes in the `vN` sequence** (drop v3, keep v2/v4/v5). Simpler — no dir renames, no repo renames — but `nextVersion` is `latest + 1`, so a later `build` would re-mint a removed number anyway, producing two different generations that each called themselves the same version at different times. Compaction keeps the sequence an honest, gapless count.
- **Delete local first, then external, best-effort.** Fewer moving parts, but it discards the deploy URL and remote before using them, so any external failure permanently orphans a live site or repo. The pointer must outlive the external teardown.
- **A separate `sb remove-version` command** instead of `--version` on `remove`. Rejected for symmetry with `sb push`, which already scopes to a Version with `--version n` (ADR-0004): one verb, one scoping flag.
- **Record the deployment id at `deploy` time** so per-Version teardown is a direct delete instead of a list-and-match. Deferred: it changes the `deploy` write path and the `SiteVersionRef` shape for a lookup that is cheap to do on demand, and matching the recorded URL against `wrangler pages deployment list` needs no migration of records already written.
